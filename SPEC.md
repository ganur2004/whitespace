## 2. Что мы строим

**Одной фразой:** владелец бизнеса описывает концепцию заведения и город, а агент через вкусовой граф Qloo находит районы, где живёт и ходит аудитория с подходящим вкусом, но мало похожих конкурентов, и показывает топ-3 зоны на карте с объяснением.

**Аудитория:**
- владельцы малого бизнеса, которые открывают новое заведение или вторую точку;
- франчайзи и управляющие сетей, выбирающие город или район;
- брокеры коммерческой недвижимости, которым нужно обосновать локацию клиенту.

**Проблема:** классический выбор места опирается на трафик, демографию и аренду. Эти данные говорят, *сколько* людей рядом, но не говорят, *понравится ли им именно эта концепция*. Рамен-бар с винилом и крафтом и семейное кафе с одинаковым трафиком могут иметь совершенно разную судьбу в одном районе.

**Язык продукта:** английский (интерфейс, ответы агента, описание). Города для демо: США (Остин, Бруклин, Чикаго). Город выбирается из списка поддерживаемых крупных городов США, который составляем на S0.

**Пример сценария:**

1. *User:* «A ramen bar with a vinyl listening corner and craft beer. Austin, TX. Places like Ramen Tatsu-Ya and Kitty Cohen's.»
2. Агент находит в Qloo якорные сущности (заведения, музыкальные жанры или артистов, бренды, которые отражают концепцию) и показывает их чипами. Пользователь может убрать лишнее или добавить своё.
3. Карта Остина окрашивается тепловой картой вкусового совпадения. Поверх отображаются существующие рамен-бары.
4. Агент выделяет топ-3 зоны, где аудитория сильная, а конкуренция слабая. Каждая зона пронумерована на карте и имеет карточку справа.
5. В карточке зоны: название района, сила совпадения, сколько конкурентов рядом, какие места любит аудитория этой зоны и почему зона подходит.
6. *User:* «Exclude downtown, rent is too high there.» Агент пересчитывает зоны без центра.
7. *User:* «Compare zone 1 and zone 2.» Агент сравнивает их по аудитории, конкурентам и вкусам.

**Чем отличаемся от других участников.** По открытым репозиториям видно, что много проектов про переезд в новый город, маркетинг для кафе и поиск партнёров для брендов. Выбора места для открытия бизнеса с анализом «аудитория минус конкуренция» мы среди них не нашли.

**Что НЕ делаем (вне рамок хакатона):** данные об аренде и пешеходном трафике, регистрацию пользователей, оплату, мобильное приложение, города за пределами США, произвольный ввод города вне списка поддерживаемых.

## 3. Почему без Qloo это не работает

Этот раздел почти дословно пойдёт в описание на Devpost, потому что это главный критерий организаторов.

- **Тепловая карта вкусов.** Только Qloo даёт по городу сетку ячеек размером около 150 м с процентилем совпадения со вкусом, заданным конкретными заведениями, артистами и брендами. Ни карты, ни демографические данные этого не дают.
- **Межкатегорийные связи.** Концепция «рамен + винил + крафт» описывается сущностями из разных категорий: заведения, музыка, бренды. Qloo связывает их в один вкусовой профиль.
- **Конкуренты с поправкой на вкус.** Мы не просто считаем рамен-бары рядом, а учитываем, насколько каждый из них совпадает с той же аудиторией. Сильный конкурент для нашей аудитории весит больше, чем случайное заведение той же категории.
- **Объяснения.** Qloo показывает, какие из якорей сильнее всего повлияли на совпадение каждого места (explainability), а общие теги мест и якорей мы считаем кодом. Поэтому агент объясняет выбор зоны фактами, а не догадками LLM.

Без Qloo проект превращается в «карту конкурентов», которую можно сделать в любом картографическом сервисе.

## 4. Что известно про Qloo API

Документация: https://docs.qloo.com/reference/qloo-llm-hackathon-developer-guide (сайт не открывается автоматическими инструментами, смотреть в браузере). Раздел сверен с документацией 12 октября 2026. Подробности, форматы ответов и шаблоны запросов — в `docs/QLOO-NOTES.md`. Всё с пометкой **[проверить]** подтвердить на этапе S0 живыми запросами.

**Базовое**
- Хакатонный ключ работает **только** с `https://hackathon.api.qloo.com`. Со staging и production он даёт `401`.
- Авторизация: заголовок `X-Api-Key`. Не Bearer и не параметр запроса.
- `/v2/insights` — только GET, параметры в строке запроса. POST с JSON-телом не работает.
- Легаси-эндпоинты `/recommendations` и `/recs` не поддерживаются.
- **Неизвестные или неподходящие для `filter.type` параметры молча игнорируются**: API отвечает 200 с пустым списком или с результатом без фильтра. Поэтому клиент проверяет параметры по своему списку разрешённых для каждого `filter.type` (раздел 13.1).
- `403` означает, что тип сущности не поддерживается. Ошибка «at least one valid signal or filter is required» означает, что ID тегов или аудиторий невалидны.
- Ответ нельзя сократить на стороне API: приходят все поля, включая объёмные `akas`. Нормализуем на сервере и не отдаём сырые ответы в браузер.
- Лимиты (проверено на S0 по заголовкам ответа): **5 запросов в секунду и 10 000 в месяц**. Их можно поднять по запросу в Discord, `#api-help`. При превышении API возвращает `429`.
- **Условия использования данных:** кэшировать ответы на своём сервере можно, без ограничения по времени. **Хранить ответы Qloo в публичном репозитории нельзя.** Поэтому в репозитории только синтетические фикстуры, а записанные реальные ответы хранятся приватно (раздел 13.2).

**Пагинация:** `take` от 1 до 50 (по умолчанию 20), `page` от 1 до 100, либо `offset`.

**Поиск сущностей:** `GET /search`
- `query`, `types` (типы для поиска отличаются от `filter.type` в insights), `filter.location` (`lat,lon`, WKT или UUID), `filter.radius` в **милях** (по умолчанию 10), `sort_by` (`match`, `distance`, `popularity`), `page`, `take`.
- Для мест из ввода пользователя передаём центр города, чтобы найти нужный филиал.

**Поиск тегов:** `GET /v2/tags`
- `filter.query`, `filter.tag.types`, `feature.typo_tolerance=true`, `feature.semantic_search=true` (бета), `take` до 50, `page`.
- Статичного списка тегов нет, только поиск.

**Insights:** `GET /v2/insights`
- `filter.type`: `urn:entity:place`, `urn:entity:artist`, `urn:entity:brand`, `urn:entity:movie`, `urn:entity:tv_show`, `urn:entity:book`, `urn:entity:podcast`, `urn:entity:video_game`, `urn:entity:destination`, `urn:entity:person`, а также `urn:heatmap`, `urn:tag` (taste analysis) и `urn:demographics`. Для игр документация пишет то `video_game`, то `videogame`; нам этот тип не нужен.
- Сигналы вкуса: `signal.interests.entities=<id1,id2,…>`, `signal.interests.tags=<tag ids>`.
- `bias.trends` по умолчанию `medium`: выдача смещена к трендам. **[проверить]** даёт ли `bias.trends=off` более стабильные результаты.
- `filter.results.entities=<ids>` ограничивает выдачу заданными сущностями. Так получаем совпадение со вкусом для конкретного списка мест.
- `backfill.cross_domain.take` (по умолчанию 20) добавляет запасные результаты, если основных мало. Поэтому выдачу всегда дофильтровываем у себя по границам города и тегу категории.
- Объяснения: `feature.explainability=true`. У каждого результата появляется `query.explainability`: какие из **входных сущностей-сигналов** повлияли на совпадение, с оценками 0–1 (от 0.1 всегда включены). Плюс сводка по всей выдаче. Если посчитать не удалось, приходит `query.explainability.warning`, а результаты остаются. Это не общие теги: общие теги считаем сами.

**Локация**
- `filter.location`: `lat,lon`, WKT (`POINT`, `POLYGON`, `MULTIPOLYGON`, долгота первой) или UUID локальности.
- `filter.location.query`: нечёткий поиск локальности по названию. Если не найдена, `400`. По умолчанию граница расширяется на меньшее из 10% диаметра и 2 414 м. `filter.location.radius=0` отключает расширение.
- `filter.location.radius`: в метрах, до 800 000, по умолчанию 15 000 для точки.
- Исключение областей: `filter.exclude.location` (WKT или ID локальности), `filter.exclude.location.query`.
- Для мест также: `filter.location.geohash` (все места, чей geohash начинается с префикса), `filter.exclude.location.geohash`, точные совпадения `filter.geocode.name`, `filter.geocode.admin1_region`, `filter.geocode.admin2_region`, `filter.location.metro`.
- Для артистов, брендов и других не-мест локация передаётся как сигнал: `signal.location` (WKT `POINT` или `POLYGON`, либо ID локальности), `signal.location.query`, `signal.location.weight`. С `filter.location` они дают 200 и ноль результатов.

**Тепловая карта (`filter.type=urn:heatmap`)**
- Параметры: `filter.location` или `filter.location.query`, `filter.location.radius`, `signal.interests.entities` и/или `signal.interests.tags`, `output.heatmap.boundary`, `heatmap.dimensions`, `filter.dimensions.price_level`, `filter.dimensions.hotel_class`, `signal.demographics.age`, `signal.demographics.gender`, `signal.demographics.audiences`, `bias.trends`.
- Возвращает **все** ячейки города, `take` и `page` игнорируются. Для Остина около 1 400 ячеек, для Бруклина около 4 800 (по чужим репозиториям).
- Ответ: `results.heatmap[]`, у каждой ячейки `location.latitude`, `location.longitude`, `location.geohash` и `query.affinity`, `query.affinity_rank`, `query.popularity`. Всё в шкале 0–1.
  - `affinity` — интерес к сигналу в этой ячейке. В примере из документации значения идут равными шагами `1/N`, то есть это уже процентиль по ячейкам. Нормализация не нужна.
  - `affinity_rank` — ранговая нормализация affinity внутри выдачи.
  - `popularity` — насколько сигнал вообще распространён в ячейке. В примере высокая `affinity` встречается и при `popularity` 0.23, то есть `affinity` не сводится к плотности.
- Точность geohash зависит от размера области: для «NYC» в примере документации geohash-6. На S0 Остин, Бруклин и Чикаго пришли в geohash-7 (1653, 2166 и около 2600 ячеек).
- Распознанная локальность приходит в `query.localities.filter`. **На деле это массив** объектов с `entity_id`, `name`, `location: { lat, lon }`; в примере документации был объект с `{ lat, lng }`, перепутанными местами. Разбор принимает оба варианта.
- Кроме общей `affinity`, в каждой ячейке есть разбивка по типам якорей: `entity_place_affinity`, `entity_brand_affinity`, `entity_artist_affinity` (P1: объяснять, какая часть вкуса сильнее в зоне).
- `entity_id` распознанной локальности переиспользуем как `filter.location` в запросах мест, чтобы область совпадала с тепловой картой.
- В документации пример с тегом в качестве сигнала (`urn:tag:genre:media:non_fiction`). По чужим репозиториям «только теги дают 0 ячеек», возможно, это касается тегов кухни. **[проверить]**. Якоря-сущности всё равно основной сигнал.
- `output.heatmap.boundary`: по умолчанию geohash, ещё город или район (`urn:entity:locality`). На S0 значение `urn:entity:locality` вернуло `500 System Error`, поэтому районы берём из мест (E7).
- `heatmap.dimensions` (`quality`, `popularity`, `hotel_class`, `price_level`) добавляет колонки `<dim>_affinity` и `<dim>_affinity_rank`, **но при этом влияет на общий рейтинг `affinity`**. В основной запрос их не добавляем, только отдельным запросом (P1: слой «ценовой уровень района» через `filter.dimensions.price_level`).

**Места (`filter.type=urn:entity:place`)**
- Полезные фильтры: `filter.tags` с `operator.filter.tags=union|intersection`, `filter.price_level.min/max` (1–4), `filter.popularity.min/max`, `filter.hours`, `sort_by` (`affinity`, `distance`, `rating`, `quality`), `bias.quality`.
- `filter.location.query` для мест в Entity Type Parameter Guide не указан. Надёжнее передавать ID локальности или WKT-полигон через `filter.location`.
- Формат мест проверен на S0: `location.lat/lon`, `properties.neighborhood` (часто `null`, запасной вариант `properties.geocode.name`), `properties.price_level`, `properties.primary_genre`, `tags[]` (в insights `id`, в `/search` `tag_id`), `query.affinity` при сигнале. Подробности — в `docs/QLOO-NOTES.md`.

**Taste analysis (`filter.type=urn:tag`)**
- Сигналы: `signal.interests.entities`, `signal.interests.tags`, `signal.location`, `signal.demographics.audiences`. Фильтры: `filter.tag.types`, `filter.parents.types`.
- Ответ: `results.tags[]` с `tag_id`, `name`, `subtype`.
- P1: «вкусовые теги зоны» — `signal.location=<полигон зоны>` вместе с якорями. Какие черты отличают аудиторию этого района. На S0 работает, но теги получаются общие («Bar», «Chicken Wings»); нужен фильтр по типам тегов.

**Демография (`filter.type=urn:demographics`)**
- Сигнал: `signal.interests.entities` и/или `signal.interests.tags`. Ответ: `results.demographics[]`, у каждой сущности `query.age` (`24_and_younger` … `55_and_older`) и `query.gender` (`male`, `female`), значения от −1 до 1 относительно среднего.
- P1: «портрет аудитории концепции» одним запросом по якорям: кто эта аудитория по возрасту и полу. Даёт брифу заземлённый ответ на «кто аудитория».

**Сравнение (`GET /v2/analysis/compare`)**
- `a.signal.interests.entities`, `b.signal.interests.entities`, `filter.type`, `filter.subtype` (`urn:tag:genre`), `model` (`descriptive`, `predictive`), `take`, `page`.
- P2: сравнение аудиторий двух зон по их местам.

**Что в документации неполно**
- Entity Type Parameter Guide не упоминает `signal.location`, `feature.explainability` и `filter.location.query` для мест, хотя другие страницы ими пользуются. Раз неподходящие параметры молча игнорируются, на S0 каждый из них проверяем сравнением ответа с параметром и без.

```
│  │ agent         │  │ scout pipeline │  │ scoring       │   │
│  │ LLM + tools   │→ │ шаги анализа   │→ │ из shared     │   │

```

**Почему так**

| Решение | Зачем |
|---|---|
| Один сервер `api`, который отдаёт и API, и собранный фронтенд | Один деплой, одна ссылка на демо, ключ Qloo только на сервере |
| Детерминированный конвейер `scout` + агент поверх | Основной анализ всегда воспроизводим и не зависит от того, что решит LLM. Агент отвечает за разбор концепции, уточнения и объяснения |
| Модель оценки в `shared`, общая для браузера и сервера | Ползунок пересчитывает зоны мгновенно и без сетевых запросов, а инструменты агента считают тем же кодом |
| Все запросы к Qloo через один клиент | Кэш и лимиты защищают квоту, а запись каждого вызова даёт панель Trace |
| Панель Trace в интерфейсе | Судьи видят, как именно используется Qloo: это прямо влияет на оценку технической реализации и решает спор при равных баллах |
| `/api/scout` отдаёт шаги потоком (SSE) | Пользователь видит, как появляются якоря, карта и зоны, вместо 15 секунд пустого экрана |

**LLM:** любая модель с поддержкой вызова инструментов. Провайдер выносится за интерфейс `LlmClient`, чтобы его можно было заменить.
- Изначально план был переиспользовать Amazon Bedrock (Converse API) из SafeZone. **Это под вопросом:** по состоянию на 11 октября у AWS-аккаунта SafeZone нулевая квота на инференс Bedrock, и агент SafeZone работает на запасном сценарии без LLM (подробности в `../safezone/docs/DEPLOY.md`).
- На S0 проверить квоту. Если она всё ещё нулевая, взять другого провайдера (Anthropic API напрямую или OpenAI-совместимый API) и до M4 убедиться, что вызов инструментов работает.
- Квота и бюджет LLM должны покрывать весь период оценки, до 16 ноября.
- У чата есть запасной режим без LLM (раздел 11.3), чтобы демо не ломалось, если провайдер недоступен.

**Пояснения к полям**
- `SupportedCity.localityId` — UUID локальности Qloo для города, записывается на S0. С ним тепловая карта и запросы мест используют одну и ту же область без нечёткого поиска по названию.
- `affinity` — совпадение ячейки со вкусом в диапазоне 0–1. В режиме `percentile` это `query.affinity` Qloo как есть (уже процентиль), в режиме `lift` — превышение над базовой картой города (раздел 8, шаг 4).
- `popularity` — `query.popularity` ячейки: насколько сигнал вообще распространён здесь. В оценке P0 не участвует, показывается в карточке зоны как «размер аудитории».
- `drivers` — из `query.explainability` места: какие якоря повлияли на совпадение и насколько. `sharedTags` — общие теги места и якорей, считаются кодом.
- `audience` — P1, портрет аудитории концепции из `urn:demographics`: возраст и пол, значения от −1 до 1 относительно среднего.
- `pressure` — давление конкуренции в ячейке, 0–1 (раздел 9).
- `opportunity` — итоговый балл возможностей ячейки, 0–1.
- `source` у якоря — кто его добавил, агент или пользователь.
- `localCompetitor` — якорь является заведением той же категории в этом же городе, то есть прямым конкурентом (раздел 8, шаг 2).
- `categoryTags` — теги **одной основной категории** концепции. Синонимы допустимы (`ramen`, `ramen shop`), смежные категории вроде `bar` — нет.
- `Zone.id` — стабильный: короткий хэш отсортированного списка geohash ячеек зоны. Если после пересчёта зона не изменилась, её профиль переиспользуется.
- `Zone.profile` — заполняется шагом 7. После пересчёта на ползунке у новых зон профиля нет, пока его не догрузит `/api/profile`.
- `ScoutEvent` с типом `result` может прийти дважды: сначала без брифов, затем с ними.
- `ChatState.cells` — ячейки в компактном виде `[geohash, affinity]`, чтобы сервер без состояния мог сам пересчитать зоны.
- `trace.params` хранится **без ключа API**. `cachedAt` заполняется, когда ответ взят из сохранённого кэша (раздел 13.1).

## 8. Конвейер анализа (`scout`)

Детерминированная последовательность шагов. Каждый шаг пишет запись в `trace` и отправляет событие `step` в поток SSE.

### Шаг 1. Разбор концепции → поисковые запросы
- Вход: текст концепции, город из списка поддерживаемых, необязательные «места как у нас».
- LLM возвращает строго JSON (схема через `zod`):
  - `anchorQueries`: 3–6 строк для поиска якорей. Минимум две категории сущностей: похожие заведения, жанры музыки или артисты, бренды, отражающие стиль. Похожие заведения желательно брать **из других городов** (известные места того же типа), чтобы тепловая карта не замыкалась на местных конкурентах (шаг 4);
  - `categoryQueries`: 1–2 строки для тегов **основной** категории (например, `ramen`). Смежные категории вроде `bar` сюда не входят.
- LLM **не придумывает ID**, только поисковые строки.
- Если LLM недоступен, используется простой запасной вариант: места из ввода пользователя + слова из концепции.

### Шаг 2. Якоря
- Для каждой строки `GET /search?query=<строка>&types=<типы>&take=5`, взять лучший результат. Для мест из ввода пользователя добавить `filter.location=<lat,lon центра города>&sort_by=match`, чтобы найти филиал в нужном городе.
- Отбросить дубли. Оставить 3–6 якорей.
- Пометить `localCompetitor = true` у якорей-заведений, которые находятся в границах города и имеют тег основной категории (теги из шага 3, поэтому шаги 2 и 3 идут параллельно, а пометка ставится после обоих).
- Вернуть их на фронтенд как чипы (событие `anchors`). Локальные конкуренты помечены на чипе. Пользователь может удалить или добавить якорь через автодополнение (`GET /api/search`). После правки шаги 4–8 перезапускаются.

### Шаг 3. Теги категории
- `GET /v2/tags?filter.query=<строка>&feature.typo_tolerance=true` для каждой строки из `categoryQueries`. Для конкурентов брать тег жанра места: `urn:tag:genre:place:...` (на S0 для рамена — `urn:tag:genre:place:restaurant:ramen`). Если точный поиск ничего не дал, повторить с `feature.semantic_search=true`.

### Шаг 4. Тепловая карта вкуса
- `GET /v2/insights?filter.type=urn:heatmap&filter.location=<SupportedCity.localityId>&signal.interests.entities=<anchor ids>`. Если `localityId` не записан, вместо него `filter.location.query=<city>`.
- Дополнительные параметры (`heatmap.dimensions` и другие) в этот запрос не добавлять: они меняют общий рейтинг `affinity`.
- **Какие якоря идут в сигнал** — решение по эксперименту E2 на S0. Если карта с локальными конкурентами в сигнале «горит» только вокруг них самих, якоря с `localCompetitor` в сигнал тепловой карты не передаются. В сигнале для конкурентов и профилей (шаги 5 и 7) они остаются.
- При поиске по названию проверить распознанную локальность (`query.localities.filter`). Ожидаемый центр берётся из `SupportedCity.center`. В документации `lat` и `lng` в этом поле перепутаны, поэтому расстояние считаем для обоих порядков и берём меньшее. Если оно больше 30 км, повторить с `filter.location=POINT(lon lat)&filter.location.radius=25000`.
- Отбросить ячейки за пределами `SupportedCity.bbox`.
- `affinity` ячейки = `query.affinity` (уже процентиль 0–1), `popularity` = `query.popularity`.
- **Сглаживание** (добавлено после S0): `affinity` каждой ячейки усредняется с восемью соседями по гауссу (σ = размер ячейки, отсутствующие соседи считаются нулём) и снова переводится в процентиль (`smoothCells` в `shared/src/scoring`). Живая карта рябит, а одиночные всплески вроде аэропорта Остина (там почти 1.0 по всем типам якорей) иначе становятся зонами. Сглаживание делает сервер один раз, клиент при пересчёте его не повторяет.
- **Режим `lift`** — включается, если эксперимент E1 на S0 покажет, что карты разных концепций почти совпадают (корреляция Спирмена по ячейкам выше 0.8). Тогда карта показывает в основном «где вообще много людей», и нужна поправка. По примеру из документации `affinity` расходится с `popularity`, так что режим, скорее всего, не понадобится:
  - базовая карта города: тепловая карта по сигналу из 10 самых популярных мест города **[проверить]**, как получить места по популярности без вкусового сигнала. Кэшируется на город;
  - `affinity = percentileRank(p_concept − p_base)` по всем ячейкам города, в диапазоне 0–1. Если ячейки нет в одной из карт, её процентиль в этой карте считается равным 0;
  - в результате `affinityMode = "lift"`, в легенде поясняется, что это совпадение выше обычного для города.
- Результат: `HeatCell[]`.

### Шаг 5. Конкуренты
- Полный список: `GET /v2/insights?filter.type=urn:entity:place&filter.location=<localityId или WKT-полигон bbox>&filter.tags=<category tag ids>&operator.filter.tags=union&take=50&page=1..4` без сигнала вкуса, до 200 мест.
- Совпадение со вкусом для **каждого** конкурента: `filter.results.entities=<id конкурентов>&signal.interests.entities=<anchor ids>&take=50`. ID передаются пачками по 50, чтобы строка запроса не превышала около 8 КБ. Сохранить у каждого конкурента его `affinity` к якорям Поле `query.affinity` (проверено на S0). Якоря-места в эту выдачу не попадают и получают полный вес.
- Если API не отдаёт поле совпадения, `affinity` не заполняется и в модели оценки `w_c = 1` для всех.
- Дофильтровать у себя: места за пределами `SupportedCity.bbox` и без тега категории отбросить (API может добавить запасные результаты).
- Шаги 4 и 5 не зависят друг от друга, поэтому идут параллельно.
- P1: ценовой уровень концепции (`$`–`$$$$`). Тогда конкурентами считаются места своего ценового диапазона: `filter.price_level.min/max`.

### Шаг 6. Оценка и зоны
- Раздел 9, код из `shared/src/scoring`.

### Шаг 7. Профили зон
Для каждой из топ-3 зон:
- `GET /v2/insights?filter.type=urn:entity:place&filter.location=<WKT POLYGON зоны>&signal.interests.entities=<anchor ids>&feature.explainability=true&take=8`. Полигон упрощается до 50 вершин, долгота первой. Если полигоны не работают, `filter.location=POINT(<lon> <lat> центра)&filter.location.radius=1200`.
- Из ответа: `tastePlaces`, название района (самое частое `neighborhood`), у каждого места `drivers` из `query.explainability` и `sharedTags` (общие теги с якорями, считаются кодом; пока не сделано).
- Сделано (реализация после S0):
  - места дополнительно проверяются на попадание в контур зоны;
  - в `tastePlaces` не попадают конкуренты (тег основной категории) и отели (`urn:tag:genre:place:hotel`, `urn:tag:category:place:hotel`): «местные любят отель» ничего не говорит о районе;
  - если внутри маленького контура меньше 3 мест, второй запрос — `POINT` центра зоны с радиусом 600 м;
  - конвейер сначала присылает зоны без профилей (карта появляется сразу), затем результат с профилями.
- В карточке: название района вместо «Zone N», до трёх мест и одна строка о том, на каких якорях держится совпадение в зоне; якоря отдельного места показываются, только если отличаются. Места выбранной зоны подсвечиваются на карте.
- Тот же код обслуживает `/api/profile`, который догружает профили новых зон после пересчёта на ползунке. Клиент хранит профили по `Zone.id`, ждёт 700 мс после последнего движения и не повторяет запрос для зон, профиль которых не загрузился. У `/api/profile` свой лимит по IP (`PROFILE_LIMIT_BURST`, `PROFILE_LIMIT_PER_MINUTE`).
- P1: «вкусовые теги зоны» — `filter.type=urn:tag&signal.location=<WKT POLYGON зоны>&signal.interests.entities=<anchor ids>` (на S0 работает, теги общие). Что отличает аудиторию района: «Locals here over-index on: …».
- P1: «культура аудитории» — артисты и бренды, популярные у этой аудитории в зоне: `filter.type=urn:entity:artist` или `urn:entity:brand` с `signal.location=<WKT POLYGON зоны>` и якорями **[проверить]**. Пригодится для маркетинговых идей в брифе.

### Шаг 7а. Портрет аудитории (P1)
- Один запрос на анализ: `GET /v2/insights?filter.type=urn:demographics&signal.interests.entities=<anchor ids>`.
- Результат: возраст и пол аудитории концепции относительно среднего (`ScoutResult.audience`). Показывается над карточками зон, и бриф получает заземлённый ответ на «кто аудитория». От зоны не зависит.
- Сделано. Qloo отдаёт демографию по каждому якорю отдельно, и якоря тянут очень разную аудиторию: в Остине Ramen Tatsu-Ya — 25–29, Lagunitas — 55+. Простое среднее превращается в «аудитория 55+» из-за одного бренда, поэтому интерфейс показывает и общий вывод, и разбивку по якорям (`AudiencePortrait.byAnchor`). Если якоря расходятся по возрасту, фраза так и говорит. Запрос идёт параллельно с тепловой картой и конкурентами; если он не удался, анализ проходит без портрета.

### Шаг 8. Брифы
- LLM пишет по каждой зоне короткий бриф (4–6 предложений): почему здесь, кто аудитория, какие конкуренты, на что обратить внимание, что проверить дальше (аренда, трафик, визит на место). Про аудиторию — только из `audience` и `drivers`, если они есть.
- **Правило заземления через токены.** LLM получает список сущностей зоны с короткими ID (`p1`, `c2`, `a3` — места профиля, конкуренты, якоря) и ссылается на них **только токенами** `[[p1]]`, не вписывая названия сам. Код подставляет названия.
- Проверка после генерации:
  - каждый токен есть в переданном списке;
  - последовательности из двух и более слов с заглавной буквы вне токенов должны быть в списке разрешённых: районы и город из данных.
- Если проверка не прошла, бриф перегенерируется один раз, затем используется шаблонный текст.
- Брифы не задерживают показ зон: сначала отправляется `result` без брифов, затем `result` с ними.

**Время выполнения:** цель до 15 секунд для всего конвейера, зоны на карте раньше. Шаги 2 и 3 выполняются параллельно, шаги 4 и 5 тоже, профили зон и портрет аудитории тоже.

## 9. Модель оценки (`scoring`)

Вынести в `shared/src/scoring/` чистыми функциями без сетевых вызовов. Один и тот же код работает в браузере (ползунок) и на сервере (конвейер и инструменты агента). Покрыть тестами в `shared/test/`.

### 9.1 Давление конкуренции

Для центра каждой ячейки:

```
pressure_raw(cell) = Σ по конкурентам  w_c · exp( −d² / (2σ²) )
w_c = 0.5 + 0.5 · affinity_c
σ = 600 м
```

- `d` — расстояние от центра ячейки до конкурента.
- `affinity_c` — совпадение конкурента с той же аудиторией. Если API его не дал вообще, `w_c = 1` (раздел 8, шаг 5).
- Нормализация: `pressure = min(1, pressure_raw / max(P95, 1))`, где P95 — 95-й перцентиль `pressure_raw` по всем ячейкам. Так один кластер конкурентов не «сплющивает» шкалу.
- Нижняя граница 1 — это один конкурент с полным весом прямо в ячейке. Без неё в городе, где все конкуренты далеко, крошечные значения растянулись бы до 1, и далёкий конкурент выглядел бы как сосед. Она же убирает деление на ноль.
- Для скорости расстояния считаются в локальной проекции города в метрах, конкуренты дальше 3σ не учитываются.

**Почему так:** гауссово ядро плавно учитывает расстояние: конкурент через дорогу важнее конкурента в километре. Вес по `affinity` отражает идею проекта: опаснее всего конкурент, который нравится той же аудитории.

### 9.2 Балл возможностей

```
opportunity(cell) = affinity · (1 − competitionWeight · pressure)
```

- По умолчанию `competitionWeight = 0.6`. В интерфейсе это ползунок «Насколько вас пугает конкуренция».
- Ячейки с `affinity < minAffinity` (по умолчанию 0.7) получают `opportunity = 0`. Нет смысла открываться там, где аудитории нет, даже если нет и конкурентов.
- Ячейки внутри `excludePolygons` получают `opportunity = 0`.

### 9.3 Зоны

1. Взять ячейки из верхних 5% по `opportunity`, но не меньше 20 штук.
2. Кластеризовать центры ячеек: DBSCAN (`turf.clustersDbscan`), `minPoints = 4`, `eps` зависит от размера ячейки:
   - шаг сетки = большая сторона ячейки в метрах для точности geohash ячеек на широте города (из `ngeohash.decode_bbox`);
   - `eps = max(400 м, 1.5 · шаг сетки)`;
   - для geohash-7 это 400 м, для geohash-6 в Чикаго около 1,4 км. С фиксированными 400 м ячейки geohash-6 (центры в 0,6–0,9 км друг от друга) не дали бы ни одного кластера.
3. Балл зоны: `score = mean(opportunity топ-10 ячеек зоны) · bonus(cellCount) / bonus(100)`, где `bonus(n) = 1 + 0.1 · ln(min(n, 100))`. Небольшой бонус за размер: большая зона даёт больше вариантов помещений. Деление на `bonus(100)` держит балл в 0–1, чтобы его можно было показать в карточке.
4. Взять топ-3 зоны. Если зон меньше трёх, ослабить пороги (верхние 10%, `minPoints = 3`) и повторить один раз. Если и после этого зон меньше трёх, вернуть сколько есть: интерфейс умеет показывать 1–2 зоны и пустой результат с подсказкой ослабить ползунок.
5. Полигон зоны: выпуклая оболочка углов ячеек зоны (`turf.convex`). Объединение квадратов (`turf.union`) на практике давало рваные MultiPolygon: выбранные ячейки не всегда соседние.
6. `centroid` — центр ячейки зоны, ближайшей к среднему центру ячеек. Так номер зоны всегда стоит внутри неё.
7. `competitorsInside` — конкуренты внутри полигона. `competitorsNearby` — внутри или не дальше 1 км от любой ячейки зоны.
8. `reasons` — 2–4 коротких факта, собранных кодом, а не LLM:
   - «Taste match in the top 2% of Austin» — по средней `affinity` ячеек зоны;
   - «2 similar venues within 1 km of the zone center; areas with this audience usually have 5» — сравнение с медианой по ячейкам, где `opportunity > 0`. Если рядом никого: «No similar venues within 1 km of the zone center»;
   - «Audience size: large / mid-size / niche» — по средней `popularity`;
   - «Locals here also love: …» — добавляется, когда загружен профиль зоны.

### 9.4 Обязательные тесты
- Конкурент рядом снижает `opportunity` ячейки, конкурент в 3 км почти не влияет.
- Конкурент с высоким `affinity` снижает сильнее, чем с низким.
- Ячейки ниже `minAffinity` и внутри исключённых полигонов дают 0.
- Без конкурентов и с одним далёким конкурентом нормализация не делит на ноль и не раздувает давление до 1.
- Скопление конкурентов на лучшем пятне выталкивает его из первой зоны.
- Исключённая зона пропадает, а её место занимает следующая.
- На синтетической фикстуре города получается ровно 3 зоны, и они не пересекаются.
- На сетке geohash-6 кластеризация находит зоны.
- Одинаковый набор ячеек даёт одинаковый `Zone.id`.

## 10. API сервера

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/health` | Проверка деплоя |
| GET | `/api/search?q=` | Автодополнение якорей (прокси к Qloo `/search`) |
| POST | `/api/scout` | Полный конвейер. Вход: `{ concept, cityId, referencePlaces?, anchors?, params? }`. Выход: поток SSE из `ScoutEvent`, последнее событие `result`. С `?format=json` возвращает только итоговый `ScoutResult` (для smoke-теста и контрактных тестов) |
| POST | `/api/profile` | Профили и брифы зон после пересчёта. Вход: `{ cityId, anchors, competitors, zones }`. Выход: `{ profiles: Record<string, ZoneProfile>, trace }` |
| POST | `/api/chat` | Агент. Вход: `{ messages, state: ChatState }`. Выход: `{ reply, result?, actions?: ChatAction[] }` |

- Пересчёт зон при движении ползунка идёт в браузере через `shared/src/scoring`, без сетевых запросов и без расхода квоты Qloo. Профили новых зон догружаются через `/api/profile`, когда ползунок отпустили (задержка около 500 мс).
- SSE идёт ответом на POST, поэтому в браузере поток читается через `fetch` и `ReadableStream`. `EventSource` не подходит: он умеет только GET.
- `state` в `/api/chat` содержит ячейки в компактном виде и конкурентов, чтобы сервер без состояния мог сам пересчитать зоны в инструментах агента. Для Бруклина это около 100–150 КБ на сообщение, для чата приемлемо.
- Ограничение частоты на IP для `/api/scout`, `/api/profile` и `/api/chat`, чтобы посетители демо не израсходовали квоту. Готовые сценарии, которые отдаются из кэша, лимит не расходуют. При превышении — понятное сообщение в интерфейсе, а не экран ошибки.

## 11. Агент (`agent`)

**Зачем агент, если есть конвейер:** конвейер отвечает на первый запрос. Агент ведёт диалог: уточняет концепцию, меняет якоря, исключает районы, сравнивает зоны, объясняет решения. Это и делает проект «агентным» по условиям хакатона.

### 11.1 Инструменты агента

| Инструмент | Что делает |
|---|---|
| `run_scout` | Полный анализ для концепции и города |
| `update_anchors` | Добавить или убрать якоря (через поиск Qloo), перезапустить анализ |
| `adjust_scoring` | Изменить `competitionWeight` или `minAffinity`, пересчитать зоны |
| `exclude_area` | Исключить район по названию или текущей области карты, пересчитать зоны |
| `profile_zone` | Подробный профиль зоны: места, причины, P1 — культура аудитории |
| `compare_zones` | Сравнить две зоны по фактам из данных |
| `explain_place` | Почему конкретное место совпадает со вкусом (explainability) |

- Каждый инструмент возвращает текст для агента и, если что-то изменилось, новый `ScoutResult` для фронтенда.
- `adjust_scoring` и `exclude_area` пересчитывают зоны кодом из `shared/src/scoring` по ячейкам из `state` и сразу догружают профили новых топ-3 зон, чтобы агент мог о них говорить.

### 11.2 Системный промпт (черновик)

```
You are Whitespace, a site-selection analyst for new venues.
You find neighborhoods where people with the right taste already are,
but similar businesses are still rare.
Use tools for every factual claim. Never invent numbers.
Refer to places, artists and brands only as [[id]] tokens taken from
tool results; never write their names yourself.
Keep replies short: 2-4 sentences, then point to the map.
Taste match is one signal, not a full site analysis: when recommending,
remind the user to check rent, foot traffic and visit in person.
```

### 11.3 Ограничения
- Максимум 6 вызовов инструментов на одно сообщение.
- `exclude_area` по названию района: если эксперимент E7 дал границы районов из Qloo, взять границу района. Иначе найти места с этим `neighborhood` среди уже полученных данных и построить выпуклую оболочку. Если не нашли, попросить пользователя выделить область на карте (P1: рисование прямоугольника).
- **Запасной режим без LLM.** Если LLM недоступен, чат разбирает простые команды шаблонами (`exclude <район>`, `compare zone N and M`, больше или меньше бояться конкуренции, `explain <место>`) и отвечает шаблонными фразами по данным. В интерфейсе пометка «Basic mode».

### 11.4 Заземление ответов
- Ответы агента проходят ту же проверку токенов, что и брифы (раздел 8, шаг 8). Районы и город можно писать текстом, они сверяются со списком районов из данных.
- Если ответ не прошёл проверку, агент получает сообщение об ошибке и пишет ответ заново один раз. Затем вместо ответа показывается шаблонная сводка по текущим зонам.

## 12. Интерфейс (`web`)

### 12.1 Экран

```
┌───────────────┬──────────────────────────────────┬────────────────┐
│ CONCEPT       │                                  │ ZONES          │
│ [текст]       │                                  │ ┌────────────┐ │
│ [город]       │            КАРТА                 │ │ ① East Aus │ │
│ [Find spots]  │                                  │ │ score 0.82 │ │
│               │   слои: Audience / Opportunity   │ │ 1 rival    │ │
│ ANCHORS       │   конкуренты · зоны ①②③          │ └────────────┘ │
│ (чипы) [+]    │                                  │ ② …            │
│               │                                  │ ③ …            │
│ CHAT          │                                  │                │
│ …             │  [ползунок: competition]         │ [Trace ▾]      │
└───────────────┴──────────────────────────────────┴────────────────┘
```

- На мобильных: карта на весь экран, панели как выдвижные листы снизу.
- Пример концепции подставлен в поле при первом открытии, чтобы судья мог нажать одну кнопку и увидеть результат.
- Три кнопки готовых сценариев (Остин, Бруклин, Чикаго).
- Город выбирается из выпадающего списка поддерживаемых городов (`shared/src/cities.ts`). Произвольного ввода нет: не нужен геокодер и не будет слабых карт по маленьким городам.
- Во время анализа шаги появляются по мере выполнения (события SSE): якоря → тепловая карта → конкуренты → зоны → профили и брифы.

### 12.2 Карта
- Подложка: OpenFreeMap (`https://tiles.openfreemap.org/styles/positron` или `liberty`), ключ не нужен.
- **Слой Audience:** ячейки geohash → полигоны (`ngeohash.decode_bbox`), заливка по `affinity` (градиент от прозрачного к насыщенному). В режиме `lift` легенда поясняет, что это совпадение выше обычного для города.
- **Слой Opportunity:** те же ячейки, заливка по `opportunity`. Переключатель между слоями.
- **Конкуренты:** круги, размер по `affinity`. Попап: название, район, совпадение со вкусом.
- **Зоны:** толстый контур, номер в центре, плавный `fitBounds` на топ-3 после анализа.
- Клик по карточке зоны → перелёт к зоне и подсветка её мест.
- Легенда с объяснением цветов.

### 12.3 Карточка зоны
- Номер, название района, балл.
- Совпадение аудитории («top 8% of the city»), конкуренты внутри и рядом.
- Размер аудитории по `popularity` ячеек зоны («large / medium / niche audience»).
- 3–5 мест, которые любит эта аудитория, с причиной совпадения: какие якоря на него повлияли (`drivers`) и общие теги.
- Бриф агента.
- Кнопки: «Explain», «Compare with…», «Exclude this area».
- Пока профиль новой зоны догружается после пересчёта, карточка показывает факты из кода (совпадение, конкуренты) и заглушку на месте мест, района и брифа.

### 12.4 Панель Trace
- Список шагов из `trace`: название шага, эндпоинт Qloo, параметры без ключа, число результатов, время, из кэша или нет, дата сохранённого ответа.
- Свёрнута по умолчанию. Это для судей: прозрачно показывает, как используется Qloo.

### 12.5 Экспорт брифа (P1)
- Кнопка «Download brief» скачивает Markdown со всеми зонами, причинами и картинкой карты (`map.getCanvas().toDataURL()`).

## 13. Клиент Qloo, кэш, демо-режим, хостинг

### 13.1 Клиент (`api/src/qloo/client.ts`)
- Единственное место, где вызывается Qloo.
- Базовый адрес из `QLOO_BASE_URL`, ключ из `QLOO_API_KEY`, заголовок `X-Api-Key`. Только GET.
- **Список разрешённых параметров для каждого `filter.type`** (по Entity Type Parameter Guide и итогам S0). Неизвестный параметр — ошибка в коде, а не тихо проигнорированный запрос, потому что API такие параметры молча отбрасывает.
- Строка запроса не длиннее около 8 КБ: длинные списки ID делятся на пачки.
- Сырые ответы нормализуются в `qloo/types.ts` и в браузер не уходят.
- Кэш в два уровня, ключ — метод + отсортированные параметры:
  - LRU в памяти, время жизни 6 часов;
  - сохранённый кэш, который переживает перезапуск (`api/src/qloo/cache.ts`): файл на приватном томе хостинга или в приватном объектном хранилище. Время жизни 7 дней, для политики ниже — без ограничения. Условия Qloo разрешают приватный кэш без ограничения по времени.
- Политика «устаревшее лучше ошибки»: если Qloo недоступен или вернул `429` после повторов, отдаём последний сохранённый реальный ответ, даже устаревший. В Trace это `cached: true` и `cachedAt`, в интерфейсе плашка «Cached Qloo data from <date>». Это реальные ответы API, а не фикстуры из репозитория.
- Ограничитель: не больше 4 параллельных запросов и 4 запроса в секунду (лимит API — 5 в секунду и 10 000 в месяц, проверено на S0).
- Повторы при `429` и `5xx`: до 3 раз с экспоненциальной паузой.
- Таймаут 10 секунд.
- Каждый вызов пишет `TraceStep`.
- Пустой ответ логировать вместе с параметрами: чаще всего это проигнорированный параметр или локация у не-мест (раздел 4).

### 13.2 Фикстуры, записи и демо-режим
**Условия Qloo запрещают хранить ответы API в публичном репозитории.** Поэтому данные разделены на два вида.
- **Синтетические фикстуры** (`api/fixtures/`, коммитятся). Скрипт `npm run fixtures` генерирует их в формате ответов Qloo: город, похожий на Остин, сетка ячеек с заложенными горячими пятнами, вымышленные места и ID. На них работают тесты и локальный запуск без ключа (`npm run demo`). В интерфейсе плашка «Demo data (synthetic)».
- **Записи реальных ответов** (`api/recordings/`, в `.gitignore`). Скрипт `npm run record` прогоняет три сценария и сохраняет сырые ответы. На сервере они лежат на приватном томе или в приватном хранилище и служат запасным вариантом для живого демо.
- `DEMO_MODE=true`: клиент читает ответы из записей, если они есть, иначе из синтетических фикстур. Флаг `demo: true` в результате, в интерфейсе плашка «Demo data» с указанием, записанные это данные или синтетические.
- **Живое демо работает на реальном API.** Записи используются только как запасной вариант, если API недоступен или квота исчерпана. Подмена всегда явно помечается, чтобы не выдавать записанные данные за живые.
- Перед каждым пушем проверять, что в репозиторий не попали реальные ответы Qloo.

### 13.3 Хостинг и доступность
- Демо обязано работать до 16 ноября 2026, 23:45 ET (конец оценки).
- Хостинг без засыпания. Бесплатный Render не подходит: холодный старт до минуты и потеря кэша при каждом засыпании. Варианты: Fly.io с `min_machines_running = 1` и томом под кэш, платный Render, AWS (опыт SafeZone). Бюджет закладываем на 4 недели.
- Если выбираем AWS Lambda: для SSE нужен режим response streaming у Function URL, а сохранённый кэш держим в S3, потому что диска между вызовами нет.
- После каждого деплоя `npm run warm -- <url>` прогоняет три готовых сценария, чтобы кэш был горячим.
- Проверка доступности раз в несколько часов до 16 ноября: cron в GitHub Actions с `npm run smoke -- <url>` или внешний пинг.
- Ключи в секретах хостинга. Квота LLM и действие ключа Qloo должны покрывать весь период оценки.
